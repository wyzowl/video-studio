# Pattern: prompt and answer

A request types into the product's real input (a chat box, a search bar, a terminal, an address bar) and the product
answers. The keyboard is the actor, the product the responder. 5–12 s.

**Beats**
0. *Optional lead-in* (2 s at most): a typed headline, a title card, the window flying in.
1. *The input takes focus:* a pill expands, a card springs in, one push crops tight onto the input, a search panel
   springs up while the page blurs behind it. Optionally an attachment dropped in or an option picked.
2. *The request types* quickly behind a caret; the box grows as it fills, and a typed name may turn into a chip.
3. *Submit and working state:* the submit is clicked, what was there clears, and the product visibly works (status
   words cross-fading with a shimmer, a spinner, a checklist ticking).
4. *The answer,* one of: built up block by block (text streaming, rows arriving, a chart drawing, the view scrolling
   to follow); a finished result appearing at once; or nothing, when the request itself is the hook.
5. *Resolve:* hold on the finished answer; a confirming click; or a second request starting before the cut (the
   loop never ends).

**As an ending:** the closing line shrinks and lifts to make room for a command pill that types the install command
and holds with a blinking caret.

**Keep:** the camera makes at most two moves, both towards or away from the input, and stays still while the answer
streams (the content scrolls, not the camera); real output from the product, never invented.

**Techniques:** type-on, status swaps, streaming text, chart draws (`../techniques/text.md`, `../techniques/data.md`).
